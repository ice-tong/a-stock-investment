# 跨工具接力准则

本仓库会被多个 Agent 工具（Claude Code、Qoder、Kimi Work 等）在不同会话、不同上下文中接力维护。
目标：**任何一个工具在新会话中接手，5 分钟内恢复到可工作状态，且不依赖上一次对话的任何记忆。**

## 一、核心原则

1. **仓库即真相**：一切持久状态必须落在 git 仓库的文件里（文档、配置、账本、订单）。不允许只存在于对话记录、剪贴板或某个工具的私有存储中。
2. **对话不可继承**：假设下一个接手者完全看不到本次对话。重要结论、决策、待办，必须在收工前写入 `docs/进展与交接.md`。
3. **环境可复现**：Python 环境一条命令可重建（见 `docs/进展与交接.md` 接手规则）；工具用法一律 `-h` 自查；核心流程不依赖某个框架特有的功能。
4. **单一事实来源**：
   - 项目级规则与角色定义 → `AGENTS.md`
   - 任务级状态与交接 → `docs/进展与交接.md`
   - 模拟交易设计 → `docs/模拟交易系统设计.md`
   - 子代理提示词 → `prompts/`
   同一信息只写一处，其他地方放链接，避免多份拷贝漂移。

## 二、开工检查清单（每个会话开始时执行）

1. `date` 确认当前日期；`git status` 确认工作区状态；`git log --oneline -5` 看最近动作。
2. 读 `docs/进展与交接.md`，按顺序看：**当前任务快照 → 当前状态 → 接手规则**。
3. 对照本文第四节的框架能力表，确认当前工具能做什么、不能做什么；用户要求的任务超出本工具能力时（如需要子代理并行、需要定时任务），明确告知用户并给出降级方案。
4. 涉及模拟交易时，先确认定时任务归属（`docs/进展与交接.md` 接手规则第 2 条），不要在第二个工具里重复配置。
5. 如果 `git status` 显示有未提交修改且不是本工具留下的，先向用户确认再继续。

## 三、收工交接清单（有实质进展后、会话结束前执行）

1. 更新 `docs/进展与交接.md`：
   - 「当前任务快照」：进行中的任务、下一步动作（带触发条件和时间）、阻塞点、待用户决策事项；
   - 「当前状态」：阶段进展有变化时更新；
   - 「工作日志」：加一行（日期、工具名、干了什么）。
2. 提交 git，提交信息注明工具名，如 `[kimi] docs: 增加跨工具接力准则`。
3. 不留半成品：代码要么能跑，要么在文件和交接文档里标注 `WIP` 及原因；`accounts/`、`orders/` 已冻结文件和 `config/risk.yaml` 绝不修改。
4. 如果本次会话做了决策（改了规则、选了方案），把"为什么这么决定"一句话写进交接文档，下一个工具不必重新推导。

## 四、框架能力与入口对照

| 框架 | 规则入口 | 子代理调度 | 定时/调度能力 | 备注 |
|---|---|---|---|---|
| Claude Code | `CLAUDE.md` → 导入 `AGENTS.md` | `.claude/agents/`（由 `tools/build_agents.sh` 生成） | 无内建能力，需外部 cron | 子代理可并行 |
| Qoder | 直接读 `AGENTS.md` | `.qoder/agents/`（同生源成） | 内建 `qoder_cron` 定时任务工具 | 子代理可并行 |
| Kimi Work | 工作区自动注入 `AGENTS.md` | **不可用**，按第五节降级执行 | Automation（cron 任务） | 适合承担定时任务 |

新增框架接入时：确认它能读到 `AGENTS.md`（读不到就在它自己的配置里导入），并在上表补一行。

## 五、无子代理框架的降级执行

当前工具不支持子代理调度时（如 Kimi Work）：

1. 依次读取 `prompts/agents/<名称>.md`，按该角色**串行**执行各维度分析，替代标准流程中的并行调度；
2. 每个维度的输出格式、数据纪律不变（遵守 `prompts/通用规则.md`）；
3. 在报告中注明"本报告由单线程降级流程产出"，提醒用户并行度与独立性有损失（各维度出自同一上下文，交叉验证强度下降）。

## 六、并发与冲突

1. 同一时间只让一个工具操作本仓库，尤其是 `python -m sim execute` / `evening` 及对 `accounts/`、`orders/` 的任何写入。
2. 定时任务全局唯一，归属记录在 `docs/进展与交接.md`；换工具承担前，先在旧工具里禁用/删除旧任务，再在新工具里创建，并更新归属记录。
3. 两个工具先后改了同一文件：以 git 提交为准，先合并冲突再继续工作；拿不准哪个版本对，问用户。
